# daedalus verify

Human-facing text (0031): Text a human reads names each item in words: a short label or one line on what it is and what it does. Ids (ruling ids, issue numbers, task codes, agent names, snake_case keys) may trail in parentheses, never replace the description. Logs, status lines and messages to other agents may use ids alone. Documents carry both.

This skill is the verify phase (0165). The orchestrator runs it inside a run, once per unit the moment the unit returns `[STATUS: COMPLETE]`, while later units build (0060). A producer's claims pass runs it in claims mode. Every stop here is the orchestrator's stop line, and the main session runs the stop command. Commands write the plugin root out in full in place of `${CLAUDE_PLUGIN_ROOT}`, because the orchestrator's hook refuses `$`, `~` and braces in a command.

## What the phase does well

The verifier judges each unit's diff against its brief, never against the coder's report (0128). The brief is the claim list: the unit's requirement section, its files list, the contract pins that bind it and the Standards Packet. The coder's report is receipts only, and agreement earns nothing.

### Rows mode

Rows mode (0228) runs once per unit of the build-only-the-ask class, the class list of the build phase's step 4 (`${CLAUDE_PLUGIN_ROOT}/skills/build/SKILL.md`). It runs after the unit's brief file is written and before its coder is dispatched. A unit outside the class skips it.

- Dispatch. Run the model command for the verifier as unit mode does (step 4). The verifier this dispatch starts is the unit's verifier from rows mode on, and it later judges the unit's diff (0231). Dispatch `verifier` with:
  - the first line `ROWS MODE.`;
  - the line `Unit worktree: <unit worktree path>`, so the rows reply sits with this unit and never with the unit verified before it;
  - the line `Brief: <brief path>`;
  - the line `Spec: <each path the brief's Contract line names>`, or `Spec: none` under `Contract: none`;
  - the line `Packs: <the brief's Packs: line>`;
  - the line `Base: <lock sha>`, the tree the rows are judged against;
  - and "Read the brief, the spec and the packs. For each numbered requirement, write the rows a correct build must pass: admitted rows (the forms the requirement says are allowed, each as the agent and folder it runs as) and refused rows (every hiding form from the hunt list and from each class the shell-semantics pack names, applied to that requirement). Each row is one line `<req n> | <agent> | <admitted|refused> | <command>`. Run nothing; no code is built yet. Reply with `[ROWS] n=<count>` as your first and last line and the rows between."
- Write. The orchestrator hands the rows text back, and the main session writes the file. The harness refuses an orchestrator write of a reply-shaped file. The main session writes the rows with the Write tool into `<unit worktree>/tests/adversarial/test_<unit-slug>_rows.py`, with each hyphen of the slug written as an underscore so the file imports as a module. The file is one parametrised test in the corpus's style, one case per row with the row text as its id. A refused row goes through `assert_denied` of `tests/adversarial/corpus.py`. An admitted row asserts `decide(<hook input>, CFG).allow` from `tests/hook_chain.py`, as `tests/adversarial/test_brace_glob.py` does. The main session commits the file on the unit branch with the subject `Add the verifier's rows for <unit id> (0228)`. It then adds the line `Rows: <that path>` to the brief file, directly after the `Packs:` line.
- Off contract. A reply whose first and last lines differ, or that reads `n=0`, is off its contract: stop and show its last 10 lines.

### Unit mode

1. When it runs (spec 5). Once per unit, after its `[STATUS: COMPLETE]` passes the branch, packet, descent and jail check rows of the build phase (`${CLAUDE_PLUGIN_ROOT}/skills/build/SKILL.md`, step 7), and before the build phase's finish merges it.
2. Map check. Before each verifier dispatch, run the map command with `--check` added: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_map.py --repo <repo> --out <repo>/docs/.tmp/daedalus/<train-id>/map --plan <plan path> --check`. Exit 0 prints `OK map: ... is current`; exit 1 means the map is stale against the tree, so rerun it without `--check` and record the new hash before the dispatch.
3. The `Read:` line. Asset exclusion (0192): first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py assets --repo <repo> --base <lock sha> --tip <b>`. Exit 0 prints `Assets: none`, or an `Assets: <tail>` line, then one `Over size: <file> (<n> bytes)` line per excluded asset file over the size limit and one `Asset root source: <file>` line per source file under an asset root; exit 1: stop and show its output. A file with a source ending is never excluded. Run it again for every dispatch, a fix pass included, because the tail holds only for the range it was printed for. With a tail, the `-U0` command below ends with it, copied exactly, so no asset file reaches the `Read:` or `Open:` line. Build it with `git -C <repo> diff -U0 <lock sha>...<b>`, the short form of `--unified=0` the hook admits: each hunk header `+<first>,<count>` gives `<file>:<first>-<first + count - 1>`, and a count of 0 gives `<file>:<first>-<first>`. Then, for each changed module, add the line of each importer its map entry `imports.<module path>.fan_in` names that imports it, from `git -C <repo> grep -n <module name> <b>`. The `Read:` line names where to look first and never replaces the full diff, whose `-` lines show a removed guard. Then build the `Open:` line (item 15), which names once, as absolute paths, every file the verifier opens: the brief file, the Contract and Standards files its packet lines name (no contract file under `Contract: none`), each file of the unit's `files:` list in the unit worktree that exists on `<b>`, the rows file of the brief's `Rows:` line, and each test file the coder's `- test` receipts run that is not on that list. The verifier opens the set in one turn and never searches for a file it names.
4. Dispatch. Each unit gets a fresh verifier (0231). A unit with a `Rows:` line goes to the verifier rows mode started for it, by the orchestrator's message. Before each fresh dispatch, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py model --repo <repo> --agent verifier` and pass its word as `model:` (spec 4). Dispatch `verifier` with:
   - the unit's branch `<b>`, and its diff base, the recorded lock sha;
   - the line `Unit worktree: <unit worktree path>`;
   - the line `Brief: <the unit's brief path from the build phase>`;
   - the line `Map: <repo>/docs/.tmp/daedalus/<train-id>/map/map.json` when that file exists;
   - the line `Read: <file>:<first>-<last>[, ...]` from step 3;
   - the line `Open: <path>[, ...]` from step 3;
   - the line `Claims: python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_claims.py`, with the plugin root written out in full; the verifier prints every range it judges through that script in one call per claims list;
   - the `Assets: <tail>` line and its `Over size:` lines from step 3, unchanged, when it printed a tail; the verifier ends its full diff command with that tail;
   - each `Asset root source:` line from step 3, unchanged; that file stays in the diff and is judged like any other;
   - the coder's `[STATUS: COMPLETE]` line with its ledger notes and the `## Receipts` block above it, as receipts only;
   - for a unit whose brief carries the `Scope:` and `Hunt:` lines of the build phase (step 4, 227), the rows pass below when it carries a `Rows:` line, else the hunt pass below;
   - and "Read the full diff `git -C <unit worktree path> diff <lock sha>...<b>`, removed lines included; the `Read:` ranges guide your attention and never bound it. Open every file of the `Open:` line in one turn of parallel Read calls before anything else, and never search with Grep, Glob or find for a file it names. Judge every requirement, the files list, every pin and every Standards Packet rule of the brief against the branch. Typecheck and lint receipts are judged from the coder's receipts block, not rerun; only a pytest run is reproduced. Class each refuted row `code` or `scope`; correct a wrong receipt and count it on the `corrected=<k>` line. Reply with `[VERDICT: VERIFIED] claims=<n>` or `[VERDICT: REFUTED] <rows>` as your first and last line."

   Rows pass (0228). For a unit with a `Rows:` line, run the rows file as the one test run and judge each row's result; hunt again only over a row the coder's diff changed or deleted, and a changed or deleted row is a `scope` refutation unless the brief names it. On a unit with a `Rows:` line the test run is the rows file alone: the full suite is the coder's receipt, judged from the receipts block and never rerun by the verifier. A unit without a `Rows:` line keeps the hunt pass as before. It keeps the verifier's test run of each `- test` receipt too. The rows file is the main session's commit, so the files claim never refutes it. The dispatch carries this line in place of the hunt pass: "Run the rows file `<rows path>` as your one test run, in the foreground, and judge each row's result. The full suite is the coder's receipt; judge it from the receipts block and never rerun it. Hunt again only over a row the coder's diff changed or deleted. A changed or deleted row is a `scope` row unless the brief names it. The rows file is the main session's commit, not the coder's, so it is never a `scope` row on the files claim."

   Hunt pass (227). A unit without a `Rows:` line whose files list holds any file of the build phase's step 4 list (`scripts/checks/` and the named jail and run files) gets one more line in the dispatch: "Run a hunt pass in round one. For each requirement, build hiding forms from the hunt list and run each against the changed check. Report every form that lets a write pass as a `code` row. The coder's pack ids are receipts, not claims; judge the diff; a rule the coder names and did not follow is a `code` row only when a brief requirement is unmet because of it." The list goes in the prompt in full, the same set of forms as the coder file's:
   - The hunt list: a leading option; a valued option whose value is a verb or a path; `--`; `-`; clustered flags; a unique long-option prefix; a path or versioned command name; a wrapper, and two wrappers stacked; a `NAME=value` prefix; an export, `declare -x` or `set -a` in an earlier segment; a subshell; a brace group; a pipe into the command; a here-string; a heredoc with a quoted and with a bare delimiter; a redirect before the command word; a `$`, backtick or glob in a word; a quoted `$`; `$'..'`.

   Name the worktree on a `Unit worktree:` line, never a `Worktree:` line, because the hook reads a resume's `Worktree:` line as a coder moving to a new unit. One verifier per unit (0231, amends 0086): a later unit never goes to an earlier unit's verifier. The verifiers run in parallel, up to `max_concurrent_builders` coders plus verifiers at once, the same cap the build phase's step 1 uses. The verifier stays warm only for a fix pass on the same unit: after a `FIX.` round, the unit's next verdict goes to the verifier that refuted it, by the orchestrator's message with the same items. Every message to a verifier names exactly one unit on its `Unit worktree:` line and asks for one verdict; a reply holding two verdicts counts as none, so each unit's verdict is asked again alone (issue 222).
5. Route the verdict. Read it from the last line; the verifier's verdict line is also its first line, and a reply whose first and last lines differ is off its contract: stop and show its last 10 lines. The reply's second line is the key line `Unit worktree: <unit worktree path>`, copied from the dispatch; a reply without it, or naming another worktree, counts as no reply for any unit and is off its contract the same way (0231). In a run the reply arrives as a digest (digest returns, 0205): the two verdict lines, the `corrected=<k>` line and a `report:` line naming the per-claim table saved under the run's `evidence/replies/` folder; read that file only when a step needs a claim the verdict line does not carry.
   - `[VERDICT: VERIFIED] claims=<n>`: make one call (0230): `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py route --repo <repo> --unit <unit id> --verdict VERIFIED`. It checks that the unit's newest verifier reply is that verdict and prints `route <unit id>: verified model=<word> refutations=<r> checks=<c>`, then one `operator check | <url or none> | <check text>` line per operator check below. The orchestrator copies the first line onto the unit's State Block row and records the unit as verified with `<n>` claims and the `<k>` of the `corrected=<k>` line above the verdict. A non-zero exit: stop and show its output; its `Next:` line is the next action. A correction never goes back to the coder and never counts as a refutation (0127). The unit is ready for the build phase's merge once its operator checks below are answered.
   - Operator checks (0164, 0192). After a VERIFIED verdict, the unit has one operator check per entry of its plan line's `operator_checks:` field. It has one more, the manifest's `dev_server` check, when `dev_server` is set and the unit touches web code: the stack declares a `vitest` or `tsc` command, or the unit's files include a `.ts`, `.tsx` or `.html` file. Read `dev_server` and `stack` from `<repo>/service-manifest.json` with `cat`. For each check, write one decision brief question in the shape of the per-finding audit prompt of the catalog, at the manifest's literacy level, such as "Open http://localhost:5173 in your browser. Does the scene load, and can the player move?", with the options `Pass`, `Fail` and `Skip`. A dev server question names its url and its check text; a plan check question names the url too when `dev_server` is set. The main session asks it. `Pass` records the answer. `Fail` is a refuted `code` row routed like a verifier refutation, by the same count of refutations on the unit. First run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py refuted --repo <repo> --unit <unit id> --operator-check "<check text>"` (issue 187). It records the Fail as one refutation, once per check text after the unit's newest verifier reply, and prints `refuted <unit id>: <count>`. A non-zero exit: stop and show its output. Then route by that count: the first goes back to that unit's warm coder as a `FIX.` message naming the failed check and the operator's words, and the second and third take the steps of the `[VERDICT: REFUTED]` bullet below. `Skip` records the operator's reason. Write each answer into the unit's evidence as `operator check | <url or none> | <check text> | <pass, fail or skip> | <the operator's words>`. Daedalus never starts, polls or fetches the site; the operator hosts it.
   - `[VERDICT: REFUTED] <rows>`: only rows of class `code` or `scope` count (0127); a REFUTED with neither is off its contract. On every REFUTED verdict, before routing the unit, make one call (0230): `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py route --repo <repo> --unit <unit id> --verdict REFUTED`. It records the verifier's reply on the unit once per reply, as the `refuted` command does (issue 187). It then records the choice of a fix pass or a fresh coder by the count below and runs the coder model command for the unit. It prints `route <unit id>: <fix, fresh or operator> model=<word> refutations=<count> checks=0`, where `<count>` is the number of refutations the unit has had, and the orchestrator copies that line onto the unit's State Block row. A non-zero exit: stop and show its output; its `Next:` line is the next action. The first REFUTED on a unit (`fix`) sends that unit's coder one fix pass with the `code` and `scope` rows, as a `FIX.` message: SendMessage(that unit's coder, "FIX. The verifier refuted: <code and scope rows>"). Its next `[STATUS: COMPLETE]` runs the build phase's checks and this phase again. Refutations become corpus (0229): before sending the `FIX.` message for a unit whose diff names a path of the audit phase's table-diff list (`${CLAUDE_PLUGIN_ROOT}/skills/audit/SKILL.md`, Table-diff form), record the unit branch head from `git -C <repo> rev-parse <b>` on its State Block row as the refuted head. The coder adds each refuted form as a named row under `tests/adversarial/` in its own worktree, in a commit before its fix, and the message to the verifier for the next verdict adds "Refuted forms: check that each form you refuted has a named row under tests/adversarial, committed before the fix, failing at that commit and passing now." On any other unit, a refuted requirement becomes a failing test in the unit's own test file. The second REFUTED on the same unit goes to a fresh coder on the `escalated` model through the build phase's second-refutation step (`${CLAUDE_PLUGIN_ROOT}/skills/build/SKILL.md`, step 5), and the run goes on (0187, issue 115). A third REFUTED on the same unit goes to the operator as a decision (0161, 0133), and the route call records no choice for it (`operator`): one question per refuted row, through the per-finding audit prompt of the catalog (`${CLAUDE_PLUGIN_ROOT}/skills/catalog/SKILL.md`), with the options `Fix it now (Recommended)`, `Skip, track or exempt it` and `Stop the run`. A `Skip, track or exempt it` pick on row `<n>` runs `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py exception --repo <repo> --ledger-id <ID> --unit <unit id> --row <n> --tracking <t> [--other <words>]` (issue 229); the main session runs it and the orchestrator never runs it. It prints `exemption recorded unit=<unit id> row=<n>/<total> remaining=<k>`. The unit merges once every row of its newest verdict is exempted; a new verdict or a new commit on the unit voids the earlier exemptions. Only the operator's pick starts another fix pass, records an exemption or ends the run.

### Claims mode

6. A producer's claims go to the verifier in a prompt whose first line is `CLAIMS MODE.`, with one `Claim: <output path>:<line> <claim>` line per claim (pin VER -> DOCT; 0136). The producers are the writer in either kind, the comparer and a planner spec at the brainstorm hand-off. The prompt carries no requirement section, so the verifier checks only the listed claims.
7. The verifier prints each named line, through `git -C <worktree> show <branch>:<file> | sed -n <first>,<last>p` for a path on a branch, else a Read at that line. Each claim gets one verdict: MATCH, WRONG VALUE, WRONG LINE, MISSING, OVERSTATED, NARROWED or WIDENED. A clause number beside a claim gets two checks: the line holds the claim, and the number names that line's clause. A claim that a mechanism enforces, refuses, checks or gates something gets two checks: existence (its definition) and attachment (a caller on the path it governs); existence alone is OVERSTATED. A claim that is not MATCH is a `code` row.
8. Rounds. The first `CLAIMS MODE.` prompt over a set of output paths is round 1 and checks every listed claim. The next prompt over the same output paths is round 2, then round 3. In rounds 2 and 3 the verifier checks every listed claim and every claim it rejected in the prior round, plus a random 20 percent sample of the rest of the prior round's claims, rounded up and at least one when the rest is not empty.
9. The reply carries the usual first and last verdict lines over the claims checked this round only. Each refuted claim over the public docs goes to the operator through the per-finding audit prompt of the catalog (`${CLAUDE_PLUGIN_ROOT}/skills/catalog/SKILL.md`).

## Evidence that ends it

- Unit mode: a `[VERDICT: VERIFIED]` verdict per unit, or every refuted row exempted by the operator's `Skip, track or exempt it` pick at a later refutation, recorded as the per-finding prompt records an exemption (0161). Each operator check of the unit has an `operator check` evidence row with the url, the check text and a pass or skip answer (0164). No hook at dispatch. The merge step (`daedalus_workspace.py merge`) refuses a unit unless its newest verifier reply is VERIFIED, or is REFUTED with every row exempted against that reply at the unit branch tip (scripts/lib/workspace.py:1082, :1275; scripts/lib/train_runner.py:1691); this is a script refusal, not a hook.
- Claims mode: a `[VERDICT: VERIFIED]` verdict over the claims, or every refuted row exempted by the operator. For claims over the public docs, the docs record (scripts/lib/train_runner.py:1902) and the push proof's docs rule (scripts/lib/audit_proof.py:703, :740) apply.

## Agents it uses

- verifier, one per unit from rows mode through its fix passes, and warm across claims rounds (Rows mode, steps 4 and 6).

## Suggested next

- `build`: for a unit the verifier refuted: the first time on its own for one fix pass, the second time by a fresh coder on the escalated model, a third time on the operator's Fix it now pick (step 5).
- `audit`: when every unit is verified and the build phase merged them.
- `release`: when a document phase's claims are verified in a repository.
