# daedalus setup

Human-facing text (0031): Text a human reads names each item in words: a short label or one line on what it is and what it does. Ids (ruling ids, issue numbers, task codes, agent names, snake_case keys) may trail in parentheses, never replace the description. Logs, status lines and messages to other agents may use ids alone. Documents carry both.

Self-Assessment mode (standing rule, binds only the model in the user's session, never a helper or an agent this skill starts): When this skill begins, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_findings.py start --repo <path>`, where `<path>` is the project folder. Keep the `since=` stamp and the `handover=` path it prints. When it prints `self-assessment: off` or `self-assessment: refused`, do nothing more for findings in this skill. Write a finding with `kind` set to `bug` when you work around this skill's text because the text failed. Write a finding with `kind` set to `feature` when the user passes over a proposal, a choice list or a step order this skill offered. Never write a finding for a change to the user's own plan. To write a finding, use the Write tool to put one JSON object with the seven fields `kind`, `skill`, `step`, `text_said`, `happened`, `model_did` and `result_changed` at the `handover=` path, then run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_findings.py save --repo <path> --since <stamp>`, where `<stamp>` is the `since=` stamp. Fill each field with one line in this skill's own words, and name no project folder. Never pass finding text on the command line, and never write a finding file in the project. When `result_changed` is `yes`, print one warning line at once saying you worked around the skill. When save prints a `refused:` line, fix the field it names and save once more. When it refuses a second time, drop that finding and name it at the close. At the close of this skill, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_findings.py show --repo <path> --since <stamp>` and print its lines unchanged, then name any finding that was refused twice. Never stop the user's work for a finding.

This skill is the settings wizard (0242). It runs in the main session, one question per turn. The setup script is the only writer: this session never edits a settings file itself and never runs any other command on one. Set `<path>` to `$ARGUMENTS` when the operator gave one and `.` otherwise.

## The question shape

Every setting is asked in the shape the brainstorm conversation uses:

- One AskUserQuestion call with exactly one question, multiSelect false. The header is `Setting <n>`, counting from 1 across the session.
- The question text says what the setting is in plain words, drawn from its `governs` text. Then it says what changes, from its `affects` sentence. Then it says the value now in words, or that nothing is set. It ends with one open question sentence about the setting that ends in a question mark, such as "Which commands run the unit tests for this project?" No closing sentence says how to answer (0251).
- The first choice is `Accept: <the proposal, cut to five words>`. Its description spells the proposal out and gives its reason in one sentence. The proposal is the key's `detected` value when the describe output has one, and the reason names the file it came from. Otherwise propose the value that fits what the describe output and the repository show, and say what you saw. Never propose a value you cannot ground that way.
- Then one to three alternatives, each a value the setting accepts, with a one-sentence description of what it does. Each choice label is two to five words; for a one-word value, write the value and its noun, such as "Plain level" (0251). The tool's own Other box is the only way to type a value; add no generic choice.
- Question text rules: plain sentences only. No key name, file path, ruling id or JSON goes in a question, a choice label or a choice description. A key name may trail in parentheses in a context line printed before the question, never inside it. You turn each answer into its JSON value yourself.
- Reading level: the value of the manifest's reading-level key (`docs.reading_level`) in the describe output when it is set, else plain. At plain, write the question text and its choices to `<path>/docs/.tmp/daedalus/setup-<YYYYMMDD>/ask-<n>.md` with the Write tool, with today's UTC date, as an `Anchor:` line holding the sentences before the question sentence, then a `Question:` line holding the question sentence alone, then a `Choices:` line and one `<letter>. <label>: <description>` line per choice. In the file, the first choice's label is written without its `Accept:` prefix, and every label is two to five words, written whole (0251). Then run `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_train.py ask-check --repo "<path>" --file "<that file>"`. Exit 0 prints `question ok`. Each `question:` line names a sentence to reword: reword it once and check again, and a second failure asks the question anyway. Exit 1 with no `question:` line means the file itself failed: write it again once, and a second such failure asks the question anyway.
- A setting whose `active` value is false is not active: nothing in Daedalus acts on it yet. Never ask it. Name it as not active when its group is walked and once more at the close.

## Writing an answer

- One setting: run `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_setup.py --set <file> <key> --value '<json>' --repo "<path>"`, where `<file>` is the entry's `file` value (`manifest`, `config` or `operator`), `<key>` is its `key` value and `<json>` is the answer as JSON.
- Use `--value` only when the JSON value consists of letters, digits, spaces and the characters `"[]{}:,._-/`, and otherwise write the JSON value with the Write tool to `<path>/docs/.tmp/daedalus/setup-<YYYYMMDD>/value-<n>.json` and pass that file instead, as in `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_setup.py --set <file> <key> --value-file "<value file>" --repo "<path>"`.
- Show the `changed:` or `kept:` line unchanged. If the command exits 1, the file's own check refused the value: show the message as written, then ask the same question once more with that message printed before it. A second refusal moves on to the next key.
- A block: a key whose `block` value is not null belongs to a group of settings saved together. The describe output's `blocks` entry with the same `file` and `key` lists its `members` in asking order and names the `required` ones. Before the first of them, print one plain line: "These next <n> settings are saved together.", with `<n>` the number of members. Ask each member in the question shape, and offer leaving it out as one choice for a member that is not required. Hold the answers and write nothing yet. Then write the block once: `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_setup.py --set <file> <block> --value-file "<value file>" --repo "<path>"`, where `<block>` is the block's `key` and the value is one JSON object of the held answers, a member left out omitted. The value rule above decides between `--value` and `--value-file` here too. A refusal of the block is shown as written and the block's questions are asked once more; a second refusal moves on. A block already set offers each member's value now as its proposal, and the value `null` clears a block.

## Steps

1. **Describe.** Run `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_setup.py --describe --repo "<path>"` with Bash. It prints one JSON document: `files`, `overlaps`, `blocks`, `keys`, `detected` and `moot`. If it exits 1, show its message unchanged and stop; the part after `Next:` is the next action. Tell the operator what the three files are in at most six short lines, from each file's `holds`, `where`, `whose` and `shared` values, then print each `overlaps` text as written. A file whose `malformed` value is not null: print that message as written, then run `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_setup.py --replace <file> --repo "<path>"` with Bash, where `<file>` is that file's `file` value, and show its output unchanged (0257). It writes nothing. Exit 1 means the file cannot be replaced: say its settings are skipped until the file is fixed by hand, and go on. Exit 0 printed the plan: ask once, in plain words in your reply and not as a choice block, "This settings file is from an older version of Daedalus, so this version cannot read it. The list above shows each value a new file would keep and each one it would leave out. I lean to replace it. Shall I replace it?" A yes runs the same command with `--write` added and shows its output unchanged. Any other answer leaves the file as it is and skips its settings. Ask this for the personal file too, since only a yes changes it. A file whose `schema_behind` value is true was written in an older layout and is still readable: run the same replace command, show the plan it prints, which lists each step from the file's number to `schema_current`, and ask the same question in plain words, saying the file is in an older layout and the plan brings it up to date (0264). A file with no schema number takes the carry plan as before. After a replace, run the describe command again.
2. **Create.** Run `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_setup.py --repo "<path>"` with Bash once, exactly as written. Show the output to the operator unchanged. Each line names one file: `written:` means the script created it, and `kept:` means the file already existed and was left as it was (0076). The one other line, `docs.reading_level: null; examples: <examples>`, follows a written service manifest: it names the reading levels the docs writer reads from `docs.reading_level`, since the file itself holds no comments (0134). If the script exits 1, show its message unchanged and stop; the part after `Next:` is the next action. When the describe output shows the personal file with `exists` false and no `malformed` message, ask one question: "Daedalus can keep your own preferences in one file in your home folder, used by every project. Create it now?" The choices are `Accept: create it now` (description: "The file starts with every preference off, and nothing acts on it yet.") and `Not now` (description: "Every project works the same without it."). On accept, run `python3 ${CLAUDE_SKILL_DIR}/../../scripts/daedalus_setup.py --create-operator` and show its line unchanged; an exit 1 shows its message and goes on. Then run the describe command of the first step again, so the later steps read the files as they are now.
3. **Day one.** Take each key whose `day_one` value is true, in the order the describe output lists them, one at a time:
   - its file is malformed: skip it;
   - its `override` value is true: skip it, since an override has a good default and is offered only in the next step (0245);
   - `moot` names it: skip it and print one line with the reason `moot` gives;
   - its `state` is `set`: skip it, since the operator already chose a value;
   - otherwise ask it in the question shape above.
   Write each answer as "Writing an answer" says. The decisions file key (`docs.decisions_filename`) is asked as one question, "Do you want decisions recorded, and in which file?" (0247). Its proposal is `decisions.md` in the docs folder, and its one alternative is `Not now` (description: "No decision is recorded, and nothing asks about decisions until you name a file."). `Not now` writes `null`. A file name the operator types is written as the name alone, never a path.
4. **More.** Print the groups not walked yet, one line each, in `order`: the group's `title` and how many of its settings are active. Ask one question, "Which group of settings do you want to walk next?", with the choice `Done` first (description: "End here and see what changed.") and then up to three groups not walked yet, in order; the Other box takes the title or line number of any group in the list. Walking a group asks each of its keys in the question shape above, one at a time, the ones already set included, and then returns to the list:
   - a key whose `override` value is true: before its question, print one line saying it has a good default that most projects keep, then ask it;
   - a key whose `active` value is false: print one line naming it as not active, and do not ask it;
   - a key whose `set_as` value differs from its `key` sits inside a list or a named entry (0257): at the first such key, ask once for the whole list or set of entries in the question shape, proposing its `value` now, and write it as "Writing an answer" says with the `set_as` value as the key and a value file; skip the later keys with the same `set_as`;
   - a key whose `settable` value is false: print its `unsettable` text in plain words, and do not ask it;
   - a key of a malformed file: skip it;
   - a key whose `block` value is not null: when the walk reaches the block's first member, ask and write the whole block as "Writing an answer" says, once per block.
   `Done` runs the close.
5. **Close.** Show every `changed:`, `written:` and `replaced:` line of this session, in the order they were printed. When one of them names the project's settings file (`service-manifest.json`), print one plain line: "Your project settings file is not committed. A run can still start with it as the only change, but its pull request will not carry it unless you commit it yourself." (0257). Name the settings that are not active yet in one sentence, in plain words, with their keys trailing in parentheses. Then name the health check as the next command: `/daedalus:doctor`.

The operator may say `stop` at any question: run the close. Running the wizard again starts at the first step with the values as they are now, and the day-one step asks nothing already set away from its default.
