---
name: run
description: Starts any piece of work with one command. Takes a task in words, a plan path, the word brainstorm and an idea, or a leading composition name (build, push or doc). In a repository it checks the preconditions and starts the orchestrator agent, which sizes the work, names the phases it picked and why, and runs them; the session relays each operator decision. In a plain folder it runs only the phases that need no repository. Never pushes on its own.
argument-hint: A task in words, a plan path, brainstorm and an idea, or build, push or doc followed by its words.
---

# daedalus run

Human-facing text (0031): Text a human reads names each item in words: a short label or one line on what it is and what it does. Ids (ruling ids, issue numbers, task codes, agent names, snake_case keys) may trail in parentheses, never replace the description. Logs, status lines and messages to other agents may use ids alone. Documents carry both.

You are the main session of this run (run command named, 0173). You find the scope, read the arguments, run the Preconditions, start one orchestrator agent, and relay between it and the operator (0060). The orchestrator sizes the effort, announces the phases it picked and runs each phase from its phase skill; its glue is `agents/orchestrator.md`. You run two phases yourself: brainstorm before the orchestrator starts, and release after it ends. You do not write application code.

Rules for the whole run:
- Read `/daedalus:catalog` first. It names every agent, the phases with their exit conditions, the musts and the per-finding audit prompt (0088, 0089).
- Your own writes go under `docs/.tmp/daedalus/`. While a run is active, the jail puts a warning into your context for any Write or Edit of yours outside that folder in the repository that holds the run, and the call runs; it never blocks the main session's Write or Edit and never prompts for it (0105, Main never prompted). Daedalus writes code only in unit worktrees.
- Start the orchestrator with the Agent tool, written below as `Agent(<name>)`; Claude Code loads it as `daedalus:<name>`. Resume it with SendMessage. Never start `claude` from Bash.
- Progress (0085): after Preconditions, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py progress --repo <repo>` and show its note unchanged; the orchestrator shows it after each phase. Print the State Block only at a stop, at a resume, and in the summary.
- The run never pushes and never merges into `main` or `master` (0001). The operator merges. The release phase (`/daedalus:run push`), a separate step after the orchestrator ends, pushes through the conductor.
- Every stop shows the operator what happened and names the next action as a `Next:` line.
- Every stop of a started run: run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_workspace.py stop --repo <repo> --reason "<what happened>" --next "<next action>"` and show its output unchanged; its `Next:` line is the next action. It shows and discards the unit worktrees, switches this repo and the Charter back to their base branches unless a dirty tree or an uncommitted contract keeps them on `daedalus/<train-id>`, and clears the run marker (0023, 0024). When the operator says continue after a stop, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_workspace.py resume --repo <repo>` first; it marks the run active again and switches back to `daedalus/<train-id>`. Then resume the orchestrator as the Relay section says.
- The stop and resume commands stay in this session, because begin and the hooks check run here and bind the run to this session's audit log.

## Scope

1. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_doctor.py --print-scope`. It prints `scope: <repository or folder>  root: <path>` (0074). Exit 1: stop and show its output; its `Next:` line is the next action.
   - `scope: repository`: go on at step 2.
   - `scope: folder`: a plain folder with no git repository. It admits only brainstorm, plan, document and verify, and no security audit runs in it (no audit in a folder, 0178). Read the arguments as step 2 says, but never start the orchestrator. `brainstorm`, a spec path and `doc` run as the Folder run section below says. Anything else, a task in words, a plan path, `build` or `push`, needs build, audit or release: stop with "A plain folder can only brainstorm, plan, write documents and check their claims. Building, auditing and pushing need a git repository. Next: open the session in a git repository, or run git init in this folder, then run /daedalus:run again."

## Arguments

2. Read the first word of `$ARGUMENTS` (spec 4.1):
   - `brainstorm`: the rest is the idea. Run the brainstorm phase here, in the main session, never in the orchestrator (brainstorm stays in main, 0179): read and run `${CLAUDE_PLUGIN_ROOT}/skills/brainstorm/SKILL.md` with the rest as its argument. Its hand-off runs the plan phase and names the plan file it wrote; go on with that file as a plan path. A brainstorm that ends with no plan ends the run.
   - `build`: the build composition. The rest is read as a task, a spec path or a plan path below, and the orchestrator prompt carries the line `Composition: build`.
   - `push`: the push composition, the release phase. It runs here, in the main session; never start the orchestrator for it. Read and run `${CLAUDE_PLUGIN_ROOT}/skills/release/SKILL.md` with the rest, an optional run id, as its argument.
   - `doc`: the doc composition. It runs here, in the main session: read and run `${CLAUDE_PLUGIN_ROOT}/skills/document/SKILL.md` in derived document mode, with that mode's rules and preconditions, and the rest as what to derive, its sources and its output folder. Its claims go to the verify phase in claims mode.
   - Anything else is the effort itself. One path to a readable file is a plan when `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/validate_plan.py <path>` exits 0, so the prompt carries `Plan: <path>`; any other file is a spec, so it carries `Spec: <path>`. Words are a task in prose, so it carries `Task: <the words>`.
   - Nothing at all: stop. Next: run /daedalus:run again with a task in words, a plan path, or the word brainstorm and an idea.

## Preconditions

3. Set `<repo>` to the parent of the directory `git rev-parse --path-format=absolute --git-common-dir` prints (the main working tree; every worktree shares it). Not a repo: stop. Next: start the session inside the target repository, then run `/daedalus:run` again.
4. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_workspace.py begin --repo <repo>` (0024). It refuses a dirty tree, reads `<repo>/.claude/daedalus/config.json` (0010; an absent config.json means the defaults: no `charter_root`, no `standards_sources`, no `policy`), probes the decision ledger (0004), creates `<repo>/.claude/daedalus/`, the folder for run state and the audit log (0035), sets `<train-id>` to the UTC time as `YYYYMMDD-HHMMSS`, creates `<repo>/docs/.tmp/daedalus/` with its `docs/.tmp/daedalus/.gitignore` so git ignores the run's scratch files and summary, branches a declared Charter to `daedalus/<train-id>` and marks the run active (0023).
   - Exit 0: it prints the first six State Block lines; copy them unchanged. The first line ends in `audit session: pending`; step 5 fills it in.
   - Exit 3: begin found no decision ledger and wrote nothing; ask the operator the question it prints, exactly.
     - An existing file: Next: add a `ledger` block naming it to `<repo>/.claude/daedalus/config.json` from your own shell (docs/project-requirements.md), then run `/daedalus:run` again.
     - Create: write `<repo>/docs/decisions.md` holding only the two table lines it prints, the header and its separator. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/append_ledger.py --probe` and show its line; it reads `seq=0`. Next: review and commit docs/decisions.md from your own shell, then run `/daedalus:run` again.
   - Exit 1: show its output unchanged and stop; begin left no run behind, so the stop command does not run. Its `Next:` line is the next action.
5. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/verify_audit_chain.py --hooks-live --repo <repo>`. It checks that this session's hooks are writing the audit log. Exit 0 prints `OK hooks live: session <id>, ...`; record `<id>` in the State Block as `audit session: <id>`. Exit 1: stop and show its output; its `Next:` line is the next action. When the output also prints a `stale agents: <names>` line, an agent file changed after this session loaded it, so this session would run the old agent text: stop and show that line. Next: start a new Claude Code session, then run /daedalus:run again.

The first six lines of the **State Block** are begin's output, with the audit session id from step 5; `agents/orchestrator.md` shows their shape. The orchestrator keeps the full block and prints it at a stop, at a resume and in the summary.

## Relay

6. Record the agent choice: run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py choice --repo <repo> --chose "one orchestrator agent runs the phases" --over "the main session runs every phase" --cost "one agent context; the session keeps only the relay"` and show its line. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py model --repo <repo> --agent orchestrator`; it prints one model word, the `agent_models` setting for the orchestrator or else its agent file's `model:` line (spec 4). Exit 1: stop and show its output; its `Next:` line is the next action. Then Agent(`orchestrator`) with `model: <that word>` and a prompt holding, each on its own line: `Repo: <repo>`, `Plugin root: <the plugin root written out in full>`, the effort line of step 2 (`Task: <the words>`, `Spec: <path>` or `Plan: <path>`), `Composition: build` when step 2 set it, and the six State Block lines. Record the agent id the call returns; every resume addresses it.
7. Read the orchestrator's last line and route it:
   - `[STATUS: ANNOUNCE] size=<size> phases=<list>`: print the announce line the reply holds, `Run <run id>: <size>, because <reason>. Phases: <list>. Reply to change it.`, unchanged. Then at once SendMessage(orchestrator, "GO.") and read its next reply from this step. Never ask the operator to confirm the size or the phases (announce and go, 0168).
   - `[STATUS: DECISION] brief=<path> questions=<n>`: read the brief file. Ask each question with AskUserQuestion exactly as the brief writes it: its header, its question, its context sentences and its options in the order given, the recommended option first. At most four questions go in one call. When the operator picks `Follow Plugin + amend global`, edit the one global rule line by hand from your own shell now and show the diff (0066); a plugin agent never makes this edit. Then SendMessage(orchestrator, "DECIDED.\n<one line per question: <header>: <the option picked>; reason: <the operator's words, or none>>") and read its next reply from this step.
   - `[STATUS: EXCEPTION] ledger_id=<id>`: the operator picked `Skip, track or exempt it` for every finding of the rejected round, and charter-docs committed the exemption ruling. Check that `<id>` is the ruling the orchestrator's last decision brief led to and that its `Exempt:` lines match the operator's picks, then for each `Exempt: <finding id> tracking=<answer>` line run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py exception --repo <repo> --ledger-id <id> --finding <finding id> --tracking <answer>` yourself, adding `--other "<the operator's words>"` on an other answer; each run records one exemption per finding beside the rejected verdict (0133, 0139). The orchestrator never runs it. Then act on each tracking answer: for `Track it` (`issue`) you file the four-field tracked-risk issue before the pull request opens; for `Skip it` (`dropped`) or `Exempt it` (`local`) the summary's `## Audit` section carries a `Deviation:` line naming the finding and its exemption row, and that line rides the pull request body (0142). Show the printed lines, then SendMessage(orchestrator, "EXCEPTION BOUND. <the printed lines>") and read its next reply from this step. Exit 1: stop with its output as the reason.
   - `[STATUS: STOP] reason=<what happened> next=<next action>`: run the stop command with that reason and that next action, and show its output. When the operator says continue, run the resume command, then SendMessage(orchestrator, "RESUMED. Go on at the step your stop named.") and read its next reply from this step.
   - `[STATUS: TRAIN_COMPLETE] summary=<path> audit_log=<path> tip=<40 hex>`: show the summary path, the audit log path and the judged tip, the integration branch commit the audit approved or the rejected round's tip whose every finding the operator exempted. Then end the run: run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_workspace.py stop --repo <repo> --reason "run complete" --next "review the integration branch, run /daedalus:audit-report <id> to read this session's audit log, then run /daedalus:run push to push the branch and open the pull request"` and show its output. The orchestrator names release as the suggested next phase; you print its command, `/daedalus:run push`, and never start it on your own.
   - Any other last line: stop with the reason "the orchestrator's reply ended off its contract" and show its last 10 lines. Next: start the run again or report the orchestrator.
8. A change from the operator. When the operator replies to an announce line, or later asks to change the size or the phases, relay the words unchanged as the last line of the next message you send the orchestrator: `CHANGE. <the operator's words>`. At an announce reply that line is the whole message, in place of `GO.`. The orchestrator sizes the run again, records a new choice and replies with a new announce line, which step 7 routes. A phase already finished stays finished.
9. If SendMessage to the orchestrator fails, never start a second orchestrator; it would start without the first one's State Block and the run's half-done state. Stop with "The orchestrator cannot be resumed. Next: start the run again; the integration branch daedalus/<train-id> and every unit branch are kept for reference." The one exception is the ledger resume below, after its `resume` command printed its line: that orchestrator resumes the stopped run for one step, not a second run.
10. While the orchestrator runs, a refused call of one of its agents comes back to it, not to you. A hook warning in your context (0106, Main never prompted) is about a call of your own session; the call ran, so read the warning and act on what it names.

## Recovery

Both paths run on a stopped run, so each starts with the resume command of the Rules section, `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_workspace.py resume --repo <repo>`, which marks the run active again. Exit 1 of any command here: stop and show its output; its `Next:` line is the next action.

- Recovery round (issue 73): after TRAIN_COMPLETE, the operator reports a commit on the integration branch `daedalus/<train-id>`, so the approved verdict no longer names its tip. Run the resume command, then `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py reaudit --repo <repo>` and show its line, `reaudit round=<n> tip=<40 hex>`. Then SendMessage(orchestrator, "REAUDIT. <its printed line>") and read its next reply from Relay step 7. The warm orchestrator runs one audit round on the new tip and replies TRAIN_COMPLETE again, or, when the round is rejected, a decision brief with one question per finding and the three per-finding choices. The operator picks for each finding; no second recovery round runs on this session's authority.
- Ledger resume (issue 3): a run stopped after its merge and before its ledger commit, so its summary holds `Ledger ids: pending`, and the operator asks to finish it. Run the resume command, then `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py resume --repo <repo>` and show its line, `resume ledger train=<train-id> summary=<repo-relative path>`. Run the Relay step 6 model command for the orchestrator, then Agent(`orchestrator`) with `model: <that word>` and a prompt holding, each on its own line: `RESUME LEDGER. <its printed line>`, `Repo: <repo>` and `Plugin root: <the plugin root written out in full>`. Record the agent id the call returns and read its reply from Relay step 7. It runs the ledger step only and replies TRAIN_COMPLETE.

## Folder run

A run in folder scope (step 1) runs every phase here, in the main session, and never starts the orchestrator (no audit in a folder, 0178). `<repo>` is the root step 1 printed, and no git command runs (0069).

- Output folder. Ask the operator where the run's outputs go, in plain words, with the three choices the runner offers: 1) the project's docs folder `<repo>/docs`, 2) a new folder under /tmp, 3) a folder they name. The second choice sets `<out>` to `/tmp/daedalus-<YYYYMMDD-HHMMSS>`, with the UTC time; the others set it to the folder picked. When the `doc` arguments name an output folder, that folder is the answer and the question is not asked.
- Begin. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_workspace.py begin --repo <repo> --scope folder --out <out>` (issue 48). It runs no git command. It takes `<out>` when it is an existing writable folder, `<repo>/docs`, or a new folder under /tmp, which it creates, and refuses any other path. It creates `<repo>/.claude/daedalus/` and `<repo>/docs/.tmp/daedalus/`, sets `<train-id>`, records the folder scope and `<out>` in the run's state and marks the run active.
  - Exit 0: it prints seven State Block lines, the last one `scope: folder  out: <out>`; copy them unchanged and take `<out>` from that last line. The first line ends in `audit session: pending`; the hooks check fills it in.
  - Exit 3: begin found no decision ledger and wrote nothing; ask the question it prints, as step 4 says.
  - Exit 1: show its output unchanged and stop; begin left no run behind, so the stop command does not run. Its `Next:` line is the next action.
- Hooks check. Run step 5's command, `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/verify_audit_chain.py --hooks-live --repo <repo>`, and act on its exits as step 5 says.
- Phases. Run each phase here with `<repo>`, `<train-id>` and `<out>` from begin. The phase agents write only where their write hooks admit them: the planner in the run folder `<repo>/docs/.tmp/daedalus/<train-id>/`, and the document agents below `<repo>`. Each phase skill names those paths for folder scope and copies each finished output into `<out>`.
  - `brainstorm`: read and run `${CLAUDE_PLUGIN_ROOT}/skills/brainstorm/SKILL.md` with the rest as its argument. Its hand-off runs the plan phase.
  - A spec path: read and run `${CLAUDE_PLUGIN_ROOT}/skills/plan/SKILL.md` with that path.
  - `doc`: read and run `${CLAUDE_PLUGIN_ROOT}/skills/document/SKILL.md` in derived document mode, with the rest as what to derive and its sources. Its claims go to the verify phase in claims mode (`${CLAUDE_PLUGIN_ROOT}/skills/verify/SKILL.md`), and the operator rules on every change-log row.
  - When the operator asks for a document phase after the plan, run `doc` the same way before the run ends.
  - Build, audit and release never run here. When the operator asks for one, run the stop command below with that request as the reason, then stop with the step 1 refusal.
- End. When the last phase ends, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_workspace.py stop --repo <repo> --reason "run complete" --next "review the outputs in <out>; nothing derived is used anywhere until its change-log rows read agreed"` and show its output. In folder scope it restores no branch and clears the run marker. Every earlier stop of the run runs the same command with what happened as its reason. A stopped folder run is not resumed: run `/daedalus:run` again.
