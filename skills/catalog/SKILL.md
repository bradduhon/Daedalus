# daedalus catalog

Human-facing text (0031): Text a human reads names each item in words: a short label or one line on what it is and what it does. Ids (ruling ids, issue numbers, task codes, agent names, snake_case keys) may trail in parentheses, never replace the description. Logs, status lines and messages to other agents may use ids alone. Documents carry both.

Read this at the start of any body of work, inside a run or not. Daedalus is an open composition over the agents below (0088): you compose each body of work yourself from the phase skills below, and no fixed recipe is the required shape (0165). `/daedalus:run` starts a run (0173): the orchestrator agent sizes the work, names the phases it picked and why, runs each phase from its skill, and the session relays each operator decision (0060). Hooks check four exit conditions today: a plan record before a coder, a worktree binding for every coder, an approved verdict on the exact tip (or the operator's exception) before a push or pull request, and the releaser as the only agent that pushes. Capturing each ruling and the merge are your duty and the operator's; no hook checks them. No hook checks the order of your steps.

When the operator runs `/daedalus:catalog`, print the agent table, the seven phase skills, the phase word map and the musts unchanged.

## The agents

Dispatch an agent as `daedalus:<name>`. Its tools are the only tools it is offered, and its hooks decide what it may touch: a producer writes only where its write hook allows, a judge and a finder read, a mover commits and pushes, a shaper writes one scratch file, and the dispatcher (the orchestrator) starts and resumes the other agents under its dispatch gate and writes only its train's scratch folder; the summary command writes the train summary. The table is generated from the agent files by `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catalog.py table`, and a test fails when this copy goes stale.

## The seven phase skills

Every body of work passes through phases, each open inside (0089). Each phase is a skill under `${CLAUDE_PLUGIN_ROOT}/skills/<name>/SKILL.md` that says how to do the phase well, the evidence that ends it, the agents it uses and which phase may come next (0165). The orchestrator reads the skill of each phase it runs.

| Phase skill | What happens | Evidence that ends it |
|---|---|---|
| brainstorm | An operator with an idea and no spec runs `/daedalus:brainstorm`, or `/daedalus:run brainstorm`, where the planner challenges the idea in rounds and writes a design spec. It runs in the main session before the orchestrator starts (0179). | The operator says the spec stands, the verifier checks its repository receipts, and the warm planner cuts the plan. No hook checks the hand-off. |
| plan | `/daedalus:plan <spec path>`, or the plan phase inside a run, has the planner cut the work into units, with edge kinds and a graph line. Inside a run it also settles the Standards Packet and every contradiction with the operator, and locks the contract or records the skip. | A validated plan record in train state before any coder starts; the hook refuses a coder dispatch without one. Inside a run, the contract lock or the `contract: skip` line; no hook checks it. |
| build | One coder per unit, each in its own worktree, briefed by file with the two packet lines. Yields route through one place, and the verified units merge in recorded order. | Every unit returned `[STATUS: COMPLETE]` on its recorded branch and merged. Every coder has a worktree binding; the hook refuses a coder whose prompt names no worktree. The finish script refuses an unverified unit. |
| verify | The verifier judges each unit's diff against its brief, never against the coder's report. In claims mode it checks each listed claim of a producer at its line. | A `[VERDICT: VERIFIED]` verdict per unit or over the claims, or every refuted row exempted by the operator. The finish script refuses to merge a unit with no recorded VERIFIED reply. |
| audit | The units merge first. Before round 1 a reachability pass lists the older rules and gates each new feature reaches (`Reachable:` lines) and, for each unit touching a jail, gate, parser or agent instruction, what an attacker could try (`Hunt:` lines). The auditor judges the merged integration tip against the run's base, the full diff every round. The compliance specialists judge units that touch IAM, keys, mTLS or infrastructure settings. A small change takes the short form. | An approved verdict on the exact tip being pushed, or a rejected verdict on that tip whose every finding carries the operator's exemption, each recorded as a ruling. The push hook and the pull request gate refuse a push or a pull request without it. |
| document | Public docs mode is the docs writer stage: the writer updates the four public docs in its own worktree, and the verifier checks each of its claims in a claims pass. Derived document mode, started with `/daedalus:run doc`, freezes the sources, derives with a receipt on every value and builds the change gate against a baseline. | Public docs: docs commits past the audited tip pass only with a docs record naming the tip they end at verified, or every refuted claim exempted; that tip is the current tip, or the commit below one ledger-only commit on top of them. Derived documents: the verifier's verdict and every change-log row agreed by the operator; no hook checks them. |
| release | `/daedalus:run push` runs in the main session. The releaser alone pushes and opens pull requests. The operator merges. | A pull request the releaser opened on the audited tip, and the operator's merge. Only the releaser pushes, and no agent merges; the operator's merge has no hook. |

Clarification and context have no skill of their own. Put each fork to the operator the moment it appears; standards and contract questions go to their specialists. Every ruling the operator made is in the ledger, captured in the session it was made; your duty, no hook checks it. Reading the task, the code and the rulings overlaps every phase, and a yield in the middle of a build is context work.

## The phase word map

The phase words on agent files are `context`, `clarification`, `plan`, `implementation`, `audit`, `commit` and `release` (phase words kept, 0176). They guide your choice of agent and never gate it. Each maps to the phase skill that serves it:

| Phase word | Phase skill | What the word covers there |
|---|---|---|
| `context` | plan | Reading the task, the code and the rulings before the cut; a yield in a later phase is context work inside that phase. |
| `clarification` | plan | The Standards Packet, every contradiction pick and the contract lock, settled with the operator before any coder starts; an idea with no spec goes to brainstorm first. |
| `plan` | plan | The cut into units, the plan record and the contract lock or skip. |
| `implementation` | build | The coders in their worktrees; the verifier's per-unit check runs in verify, and the writer and comparer run in document. |
| `audit` | audit | The compliance judges and the security audit on the merged tip; the docs writer runs in document. |
| `commit` | release | The releaser's commit and push; charter-docs commits the ledger at the audit phase's ledger step. |
| `release` | release | The push, the pull request, the CI watch and the hand-off of the merge to the operator. |

Phases overlap freely. A phase's weight scales with the task: a fix of at most 3 files and no control file carries a one-unit plan and no contract packet (0182), and a cross-module build carries the packet. Choose the weight before the phase starts and print it with its reason through the choice record.

## The musts

These are musts, not suggestions.

1. All work is audited and passes before it leaves a workspace, or the operator accepts the exception as a ruling with the findings it waives. Nothing is pushed and no pull request is opened until train state holds an approved verdict on the exact tip being pushed, or a rejected verdict on that tip with an exemption for every one of its findings (0133). The hooks refuse such a push or pull request from an agent, and warn the main session in context about its own (0106, Main never prompted); never argue with a refusal and never work around it.
2. No coder starts without a plan record and a worktree binding.
3. Every ruling is captured in the ledger in the session it is made.
4. Every choice is printed with its alternative and its cost before it is taken. Inside a run, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/daedalus_train.py choice --repo <repo> --chose "<what>" --over "<alternative>" --cost "<time or tokens>"` and add `--phase <name>` for a weight choice; it records the choice and prints `Chose <what> over <alternative>: <cost>`. Outside a run, print that same line in your reply.

## Composition rules

- One command (0173, spec 6): `/daedalus:run <task>`, a plan path or a spec path starts a run, and the orchestrator sizes it and announces the phases it picked. Three named compositions keep a fixed order: `/daedalus:run build <task>` runs plan, build, verify, audit and document; `/daedalus:run push [<run id>]` runs release in the main session, with one audit recovery round first when the tip moved after the verdict; `/daedalus:run doc <what, sources, folder>` runs document in derived document mode, verify in claims mode, then the change gate and the present step.
- Phase 1 overlap (0082): the contract stage starts the moment the last contradiction pick is made, in parallel with the pick recording and the standards re-check. The re-checked Standards Packet reaches contract-spec as an amendment it folds in before saving, and the lock waits on both.
- Packets by hash (0083): the Standards Packet is written once to `docs/.tmp/daedalus/<train-id>/standards-packet.md` after the pick commit. Every worker brief carries `Contract: <path> sha256=<hex>` and `Standards: <path> sha256=<hex>` in place of a pasted packet. The coder's `[STATUS: COMPLETE]` line ends `contract=<12 hex> standards=<12 hex>`, and a mismatch stops that unit.
- Brief by file: each dispatch's brief is a file under `docs/.tmp/daedalus/<train-id>/briefs/`, holding the unit's section of the plan verbatim, the two packet lines, the `Pick ledger ids:` line and one reminder line. Print each dispatch as three lines, `Dispatch: <agent>`, `Prompt file: <path>` and `Expect: <reply lines>`.
- Warm dispatch (0086): a unit whose dependency a running coder built goes to that coder as a resume, carrying its context. A cold coder starts only when no warm coder built a dependency of the unit.
- Rebinding (0086): a warm resume onto a new unit rebinds the coder only through the orchestrator's SendMessage, whose dispatch gate moves the coder's binding as the message goes out. The main session's SendMessage does not rebind, so a recipe the main session drives by hand cold-dispatches each new unit.
- Verifier step (spec 5): once per unit, after its `[STATUS: COMPLETE]` passes the branch, packet and merge-base checks and before finish merges it, the orchestrator sends the verifier the unit's brief, and the verifier judges the diff against its requirements, files list, pins and Standards Packet; the coder's reply is receipts only (0128). A wrong receipt is corrected in the verdict and counted on a `corrected=<k>` line, never refuted (0127). Only `code` and `scope` rows count: `[VERDICT: REFUTED] <rows>` sends the coder one FIX pass with those rows; a second REFUTED on the same unit stops the train. The verifier stays warm across units.
- Jail check units (spec 3.3): a unit whose changed files include a path under `scripts/checks/`, or `scripts/lib/jail.py`, `scripts/lib/shell.py` or `scripts/enforce_agent_jail.py`, runs `python3 -m pytest tests/adversarial -q` and ends its COMPLETE line with ` adversarial=pass`. These paths are `JAIL_CHECK_PATHS` in `scripts/lib/plan_record.py` (0182).
- Audit loop (0109, 0112, 0133): the auditor works in the audit worktree `<train-id>-audit`, created before the first round. Before each later round its refresh fast-forwards the audit branch to the integration branch, and a diverged or dirty audit worktree stops the refresh instead of losing a commit. Each blocking finding is a failing test under `docs/.tmp/daedalus/<train-id>/audit/round<n>/`, and a fix brief carries the node ids and test file paths. The verdict command only records the round; no round budget applies. Each finding goes to the operator through the per-finding audit prompt below, and only the operator's pick starts a fix round, records an exemption or ends the train.
- Recovery round (issue 73): when a commit moves the integration tip after an approved verdict, the main session runs `reaudit`, and one audit round judges the new tip. The run entry (`/daedalus:run`) relays it to the warm orchestrator as `REAUDIT. <the reaudit line>`; the release phase (`/daedalus:run push`) runs it itself when its verdict check refuses a moved tip. A rejected recovery round goes to the operator through the per-finding audit prompt below; no second recovery round runs on one tip.
- Docs writer stage (0131, 0134): after the security verdict record, the writer writes the four public docs (`README.md`, `docs/howto/README.md`, `docs/guardrails.md`, `docs/project-requirements.md`) in the worktree `<train-id>-docstage`, which takes no coder by dispatch or resume, and the verifier checks its claims in a claims pass. A verified pass merges the docs branch and records `daedalus_train.py verdict --gate docs --status verified --judged <sha>` on the merged tip, where `<sha>` is the docs branch head the verifier judged. Each refuted claim goes through the per-finding audit prompt below; once every refuted claim is exempted, the docs branch merges and `--status refuted --findings <path>` records it. The summary runs after the docs record, and the train completes only after both verdicts. The push proof admits commits past the judged tip only when each changes nothing but the four public docs and the docs record covers the tip those commits end at, before one ledger-only commit on top of them; any other move is refused.
- Ledger resume (issue 3): a train stopped after its merge and before its ledger commit resumes for that one step. The main session runs `resume` and starts a fresh orchestrator with `RESUME LEDGER. <the resume line>`, which runs the ledger step, records the verdict and rewrites the summary.
- Summary command last (issue 73, 0046): the audit phase records the ledger commit, then the approved verdict, then runs `daedalus_train.py summary`, which rewrites the summary from train state and the audit log; the push proof anchors on that command's record, and a Write of the summary never satisfies it.
- Models (spec 4): each persona's model comes from `daedalus_train.py model --repo <repo> --agent <name>`, which prints the `agent_models` setting for that agent or else the agent file's `model:` line.
- Charter-docs reads (0084): charter-docs may read what it is told to append or edit. Its brief names the absolute path of append_ledger.py.
- Ledger entry files read-only before the agent: write each ruling's entry file under `docs/.tmp/daedalus/`, make it read-only, and brief charter-docs with the ruling id and the file path only.

## Commands and reply lines the records answer to

Paths here are relative to the plugin root.

- The plan validator: `python3 scripts/validate_plan.py <path> [--max-concurrent N]` prints `OK plan: <graph line>`, or one defect line per failed check and a line naming the next action.
- The planner ends with `[STATUS: PLAN] path=<path> units=<n> critical_path=<k> width=<w>` or `[STATUS: QUESTION] <what the task leaves open>`. It may also ask for an outside fact with `[STATUS: YIELD_WEB] <query>`. In challenge mode, under `/daedalus:brainstorm`, it ends a round with `[STATUS: ROUND] round=<k> items=<m>`, `[STATUS: SPEC] round=<k> path=<path> open=<m>`, `[STATUS: NOT_VIABLE] round=<k> <the blocking fact in one line>`, `[STATUS: YIELD_WEB] <query>` or `[STATUS: QUESTION] <what the task leaves open>`.
- The train runner records the operator view and the gates' inputs: `daedalus_train.py progress`, `choice`, `plan` and `exception`, each with `--repo <repo>`.
- The verdict record: `daedalus_train.py verdict --repo <repo> --status rejected --round <n> --findings <path> --tip <sha>` records the round and prints `recorded rejected round=<n> findings=<k>`; `--status approved --round <n> --tip <sha>` records the judged tip. The docs record (0131): `daedalus_train.py verdict --repo <repo> --gate docs --status verified --judged <sha>`, which refuses when the merged docs commits end at another sha, or `--gate docs --status refuted --findings docs/.tmp/daedalus/<train-id>/docs/findings.txt` records the docs verifier's verdict on the integration tip and prints `docs verdict recorded status=<s> tip=<12 hex>`; the exemption record of a refuted docs claim lands in that docs record and prints `gate=docs` in place of `round=<n>`.
- The exemption record (0133, 0139): `daedalus_train.py exception --repo <repo> --ledger-id <id> --finding <finding id> --tracking <dropped|issue|local|other> [--other <words>]` records one finding's exemption beside the rejected verdict and prints `exemption recorded finding=<id> round=<n> ledger=<id> tracking=<answer> remaining=<k>`; it runs from the main session only.
- The recovery and resume records (0119): `daedalus_train.py reaudit --repo <repo>` prints `reaudit round=<n> tip=<40 hex>` and `daedalus_train.py resume --repo <repo>` prints `resume ledger train=<train-id> summary=<repo-relative path>`; both run from the main session only. `daedalus_train.py ledger --repo <repo> --sha <sha> --ids <ids>` prints `ledger recorded sha=<sha> ids=<ids>`. `daedalus_train.py summary --repo <repo>` writes `docs/.tmp/daedalus/<train-id>-summary.md` and prints `summary written train=<train-id> path=<repo-relative path> ledger=<pending or recorded>`. Each refusal exits 1 with a `Next:` line.
- The model choice: `daedalus_train.py model --repo <repo> --agent <name> [--override <model>]` prints the effective model word alone on one line, inside or outside a train.
- The audit worktree refresh: `daedalus_workspace.py refresh --repo <repo> --name <train-id>-audit` fast-forwards the audit branch with `git merge --ff-only` and prints the worktree path.
- The control cost table: `python3 scripts/audit_report.py --repo <R> --session <S> --controls` prints the blocks per hook, the seconds each block cost, the seconds each agent took to its first write, and the mean judge time.
- The token table: `python3 scripts/token_economy.py report --run <train id>` (or `--session <S>`) prints one row per agent and unit or audit round, then a totals row and the per-unit and per-round means, agents only; `history` prints the totals row of every saved run (`/daedalus:token-report`).

## The per-finding audit prompt

Every rejected round puts each finding in its findings file to the operator as one decision question, plus the tracking question on an exemption (0133). The verdict command only records the round; no round budget applies, and no fix round starts without the operator's pick. In a Build Train the orchestrator writes it as a decision brief and the session asks it.
Put it to the operator with AskUserQuestion, in the decision-brief shape (0103), one question per finding:
- Question: the first line states what is at stake in one plain sentence, then asks, ending in a question mark, such as "A ledger write can land outside the ledger file. What do we do with this finding?"
- Context: Two or three short sentences in the operator's words on what breaks and what happened in the test, and, for a finding that came back after its fix, what the fix missed. They name no mechanism: no ruling ids, agent names, script names or snake_case keys.
- Choices, exactly these three labels in this order, each with what it does; the how of a fix stays out of the option text and lives in the finding file:
  - `Fix it now (Recommended)`: runs a fix round. The responsible coder resumes warm with this finding's failing test, and the audit runs again on the new tip.
  - `Skip, track or exempt it`: exempts the finding. It stays in the merged work, a second question asks how the exemption is tracked, charter-docs records the exemption as a ruling that names the finding, and the main session records it with the train runner's exception command.
  - `Stop the run`: ends the run. The run stops through its stop command, and every unit branch stays for fixes by hand or a narrower rerun.
- Recommendation: The recommendation and its reason, in one sentence. The recommended choice, `Fix it now (Recommended)`, is listed first.
- Tracking question, a second prompt asked only after `Skip, track or exempt it`, never a fourth choice: a plain question such as "How do we keep track of this finding?", with context sentences saying what each answer leaves behind. Every choice is offered in every environment, with no choice withheld for any project or rule:
  - `Skip it`: drops the finding silently, stored as `dropped`. Nothing beyond the exemption row records it, and the pull request body carries a `Deviation:` line naming the finding and its exemption row.
  - `Track it`: a GitHub tracked-risk issue, stored as `issue`. The main session files the four-field tracked-risk issue before the pull request opens.
  - `Exempt it`: the local ledger record alone, stored as `local`. The ledger row records the exemption, and the pull request body carries the same `Deviation:` line.
  - Other: the operator's own words, recorded with the exemption and stored as `other`.
  The recommendation and its reason follow, in one sentence, as above.

Record each pick through the choice record, then act on the round's picks together. Never start a fix round without a `Fix it now` pick, and never stop the run on your own authority. A `Stop the run` pick stops the run; otherwise a `Fix it now` pick runs a fix round for the findings it names; when every finding is exempted, the train goes on to the ledger step and the main session records one exemption per finding with `daedalus_train.py exception --repo <repo> --ledger-id <id> --finding <finding id> --tracking <dropped, issue, local or other>`. The same prompt follows every later rejected round.
